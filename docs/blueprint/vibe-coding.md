# 地图优先的个人 Vibe Coding 蓝图

> 状态：v1.1 提案已实现入口与状态投影，文字蓝图和 Archify 投影同步维护。
>
> 适用范围：单 Owner、单 Agent、一个主要代码仓库。多人协作、团队 Flow、发布平台和外部系统仍由目标仓库自己的流程接管。

## 1. 目的地模型

这套工作流把开发任务看成一张从“现状节点”走向“目的地节点”的有向图。目的地不是“代码写完”，而是一个可以被观察和验收的状态；路线不是愿望清单，而是由事实、前置条件和验证证据连接起来的节点序列。

每次任务至少定义以下字段：

| 字段 | 要回答的问题 | 例子 |
| --- | --- | --- |
| `destination` | 最终要出现什么可观察状态？ | 登录接口拒绝未完成设备验证的请求 |
| `value` | 谁在什么场景获得什么结果？ | 已登录用户的账户更安全 |
| `acceptance` | 用什么证据判定达到？ | 失败测试存在，认证回归测试通过 |
| `scope` | 本轮允许改什么？ | API、认证服务和对应测试 |
| `non_goals` | 明确不做什么？ | 不改客户端协议，不新增 provider |
| `current_state` | 现状有哪些已验证事实？ | 当前接口只校验密码 |
| `unknowns` | 哪些未知会改变路线？ | 设备绑定字段是否已存在 |
| `boundaries` | 哪些动作需要停下来授权？ | 发布、凭证、外部写入、不可逆清理 |

### 状态标签

蓝图中的陈述必须带有可辨识的状态：

- **已验证事实**：来自代码、配置、测试、运行日志或命令输出。
- **来源说明**：来自用户、已有文档、第三方资料，尚未由当前仓库验证。
- **假设**：为了继续探路而暂时采用，必须列入未知项或风险。
- **提案**：尚未批准的路线、设计或实现选项。
- **已实现**：已经写入并通过对应节点验证的结果。
- **未验证**：计划做但尚未实际执行的检查，不能写成完成证据。

## 2. 触发词协议

固定的正向触发词是防止“聊着聊着直接开工”的低成本控制点。下列语句才改变阶段：

| 用户语句 | Agent 必须做什么 | 允许写入代码吗？ |
| --- | --- | --- |
| `进入地图优先模式` | 读取仓库事实，建立或恢复地图，收敛目的地和路线 | 不允许 |
| `地图已批准，进入施工` | 固定目的地，选定唯一当前节点，准备写入门槛 | 仅在通过 `gate` 后允许 |
| `执行地图节点 N` | 只实施 N，运行节点验收并记录证据 | 允许，范围限于 N |
| `发现偏差，重新规划` | 停止当前施工，记录新事实，重算未完成路线 | 不允许，除非只是保存地图 |
| `进行到达审计` | 对照目的地、验收、非目标和风险做最终复核 | 不允许新增功能 |

“继续”“开始做吧”“按计划来”属于内容请求，不是阶段切换。收到它们时先报告当前阶段、目的地状态、活动节点和下一步触发词。没有批准目的地或唯一节点时，产出问题和地图，不产出代码。

## 3. 主路径蓝图

下表是默认路线。小任务可以把多个节点压缩在一次对话里，但不能删除目的地、验证和偏差出口。

| 节点 | 阶段 | 输入 | Skill 介入 | 主要产物 | 写入门槛 | 出口条件 |
| --- | --- | --- | --- | --- | --- | --- |
| N0 入口 | `wayfinding` | 用户目标、约束、上下文 | `mapflow` | `.mapflow/state.json` 初始投影 | 无代码写入 | 目标仓库和任务规模已识别 |
| N1 定形 | `wayfinding` | 用户结果、价值、边界 | `destination-shaping` | Destination Contract | 无代码写入 | 目的地、验收、范围和非目标可判断 |
| N2 勘探 | `wayfinding` | 目的地、仓库和项目约定 | `repository-recon`；必要时 `domain-modeling` | Recon Report（事实、影响面、未知项） | 无代码写入 | 关键影响面有来源，未知项有探针或阻塞 |
| N3 成图 | `wayfinding` | 目的地和勘探报告 | `blueprint-planning`；必要时 `grilling`、`wayfinder`、`prior-art` | Blueprint Map、节点顺序、分支、回滚 | 用户批准前不施工 | 第一条可执行路线和唯一第一个节点已写入 |
| N4 批准 | `wayfinding` -> `implementation` | 地图和当前路线 | `mapflow` | `destination_status=approved`、`current_node` | 用户明确批准 | `gate` 通过，且当前节点唯一 |
| N5 切片 | `implementation` | 已批准地图的当前节点 | `node-slicing` | Work Item、声明写集、节点验收 | 仍不写业务代码 | 执行者无需猜测做什么、改哪里和怎样算完成 |
| N6 施工 | `implementation` | Work Item、写入范围 | `node-delivery`；内部按需 `tdd`、`diagnosing-bugs`、`flow-executor` | 代码、测试、配置或文档改动 | `node .mapflow/mapflow.mjs gate` | 节点改动完成，未超出声明写集 |
| N7 证明 | `implementation` 内的完成动作 | 节点产物和预期状态 | `node-delivery`；非微小改动追加 `code-review` | Evidence Record、测试/构建/diff/审查证据 | 只接受实际运行结果 | `verify --node N --evidence ... --command ... --observed ... --model ... --reasoning ...` 成功，或进入重规划 |
| N8 到达 | `arrived` | 全部节点证据、目的地和风险 | `mapflow`；产品价值按需另行验证 | 到达审计、最终回报、遗留风险 | 不新增未规划功能 | 目标状态出现，验收真实，非目标保持排除 |

### 3.1 N0-N2：入口、定形和勘探

动作顺序：

1. 读取目标仓库根 `AGENTS.md`、README、贡献说明和构建/测试入口。
2. 读取 Git 状态、最近相关改动、配置和相关模块。
3. 把每个结论标成“已验证事实、来源说明、假设或未知”。
4. 识别调用方、被调用方、共享契约、镜像/生成物和回归边界。

完成标准：Destination Contract 已写明可观察结果和边界；Recon Report 能让每个关键事实追溯到来源，尚未确认但会改变实现的点都有探针或问题。

### 3.2 N3：目标与路线收敛

`grilling` 只解决当前最上游、会改变实现的决策，一次只收敛一个 frontier。典型问题是：目标用户和价值是什么、兼容性边界是什么、失败时应拒绝还是降级、是否采用现有方案。

按未知项选择探针：

- `prior-art`：新 CLI、工具函数、集成、方案或机制；先查仓库和公开生态。
- `research`：需要一手资料、协议、API 或外部事实；把来源和置信度写回地图。
- `prototype`：状态模型、交互逻辑或设计疑问；一次性验证，不把原型当生产实现。
- `domain-modeling`：术语冲突、上下文边界或长期架构取舍；维护上下文和 ADR。

完成标准：目的地可以写成一个可观察状态；范围、非目标和验收不会因当前已知信息而出现两种不同实现；剩余未知都有明确探针、成本和停止条件。

### 3.3 N3-N5：成图、批准与切片

地图节点采用以下最小契约：

```yaml
id: N5
kind: implementation
title: 为认证服务增加设备验证
inputs: ["N3 的已批准路线"]
skills: [tdd]
writes: ["src/auth/**", "tests/auth/**"]
preconditions: ["destination_status=approved", "current_node=N5"]
expected_state: "未完成设备验证的请求被拒绝"
verification: ["npm test -- auth"]
on_failure: "replan"
```

批准动作锁定的是目的地和当前路线，不是永远不变的实现细节。施工中出现新事实时，保留已经验证的节点，暂停未完成节点，并进入 `发现偏差，重新规划`。目的地本身变化时，必须重新获得用户批准。

### 3.4 N6-N7：按节点施工和证明

写入前执行：

```text
目的地已批准 + 当前节点唯一明确 + gate 通过
```

节点内部使用最小充分的工程能力：

- 行为变化且测试形状清楚：先 `tdd`，再实现和重构。
- 已知 bug、回归或性能下降：先 `diagnosing-bugs`，证据定位后再改。
- 目标仓库已有 Flow 简报和 `dispatch` 门禁：才加载 `flow-executor`。
- 共享接口、结构性变更或非微小改动：完成后加载 `code-review`，从固定基线审查规范和需求两条轴。

节点验证应从便宜到昂贵：语法/类型/格式、受影响模块定向测试、必要的集成或构建、真实界面检查、最终 diff 和生成物检查。验证结果必须记录命令和真实输出摘要，不把“应该通过”写成证据。

完成标准：节点预期状态出现；声明写入范围内的改动均有解释；验证命令实际执行；失败、未验证项和风险已进入地图或回报。

### 3.6 模型策略

模型选择是按节点风险调整的执行参数，不是目的地或验收条件。蓝图可以在 `model_policy` 中写推荐值，节点可以用 `model_profile` 覆盖；状态证据另外记录实际使用的模型和推理强度。

默认建议：

| 场景 | 推荐 | 理由 |
| --- | --- | --- |
| 目的地定形、关键未知、路线收敛 | `gpt-5.6-sol` + `high` 或 `xhigh` | 需要暴露假设、比较路线并控制遗漏 |
| 普通节点施工、已有 Work Item 的局部实现 | `gpt-5.6-sol` + `medium` 或 `gpt-5.6-terra` + `medium` | 边界已锁定，降低无关设计和实现漂移 |
| 复杂调试、结构性 review、验收证据矛盾 | 升级到 `gpt-5.6-sol` + `high` | 先提高诊断和审查质量，再决定是否继续施工 |

模型推荐不能替代证据。记录实际模型时，仍要分别标注真实执行结果、模拟结果、推测和未验证项；较弱模型输出的“完成”不会绕过节点 `verify` 或最终到达审计。

### 3.5 N8：到达审计

到达审计不是“最后一次聊天总结”，而是四项判定：

1. 目的地状态是否真实出现？
2. 每一项验收是否有实际执行的证据？
3. 非目标是否仍然被排除？
4. 剩余风险、未验证项和外部动作是否已经明确回报？

四项都能回答时才调用：

```bash
node .mapflow/mapflow.mjs arrive --confirm "目标、验收、非目标和遗留风险已审计" --acceptance A1
```

`arrived` 只表示本轮工程目标和验收已审计，不表示产品价值、生产安全、公开发布或部署成功已被证明。

## 4. 偏差、重规划和暂停

以下任一情况都不是“继续试试看”，而是地图事件：

- 实际调用方或共享契约与勘探结论不同；
- 当前改动超出节点写入范围；
- 测试结果与预期矛盾，或没有可靠机器验证；
- 新依赖、公开接口、数据迁移、安全、部署、删除或外部系统动作进入范围；
- 用户价值、授权边界或目的地本身发生变化。

重规划动作：记录新事实和证据，标记受影响节点，保留已验证节点，删除不再成立的边，补充探针或新节点，然后回到 `wayfinding`。没有用户授权时停在可回滚状态。

## 5. Skill 介入矩阵

| Skill | 介入位置 | 它解决什么 | 不应承担什么 |
| --- | --- | --- | --- |
| `mapflow` | 全流程入口、状态和门槛 | 阶段路由、地图优先、节点门槛 | 代替领域判断、产品授权或测试 |
| `destination-shaping` | N1 定形 | 生成 Destination Contract，收敛价值、验收和边界 | 扫描仓库或选择实现路线 |
| `repository-recon` | N2 勘探 | 生成 Recon Report，覆盖事实、调用面、契约、生成物和回归面 | 代替产品决策或实施代码 |
| `blueprint-planning` | N3 成图 | 生成节点路线、转移条件、探针和回退分支 | 代替用户批准或直接施工 |
| `node-slicing` | N5 切片 | 把当前节点转换为 Work Item 和声明写集 | 重定义目的地或产生节点结果 |
| `node-delivery` | N6-N7 | 在写集内实施，验证并记录 Evidence Record | 宣布产品价值、生产安全或发布完成 |
| `grilling` | N2 收敛 | 暴露隐含假设，收敛关键取舍 | 直接实现代码 |
| `research` | N2 探针 | 一手资料和外部事实 | 把来源说明当仓库事实 |
| `prior-art` | N2 探针 | 复用优先，裁决采用/改造/自研 | 无证据地引入通用抽象 |
| `prototype` | N2 探针 | 快速验证状态或交互疑问 | 把一次性原型当生产质量 |
| `wayfinder` | N3 成图 | 持久化目的地、路线票和探针 | 代替用户批准 |
| `domain-modeling` | N1/N2 长期取舍 | 术语、上下文和 ADR | 解决一次性局部命名 |
| `tdd` | N5-N6 | 红-绿-重构和行为回归 | 代替产品验收 |
| `diagnosing-bugs` | N5-N6 bug 分支 | 证据定位根因和回退 | 在原因未知时盲改 |
| `flow-executor` | 仅在采用 Flow 的目标仓库 | 领取简报、dispatch、verify、回填 | 把团队门禁强加给个人任务 |
| `code-review` | N6 非微小改动 | 规范、需求、耦合和回归双轴审查 | 宣布产品价值或发布完成 |
| `session-handoff` | 跨会话/换工具/换仓库 | 保存目标、状态、证据和下一步 | 正常连续工作中的额外交接 |
| `retro` | 摩擦明显时 | 记录入口、指针、验证或工具改进 | 代替当前任务收尾 |

## 6. 能力状态审计

能力是否独立分发，取决于是否有稳定的用户问题、输入输出和完成条件。当前五个核心能力已按此标准落盘；其他候选保持按需或停放。

| 能力 | 当前状态 | 当前职责 | 后续观察或新增条件 |
| --- | --- | --- | --- |
| `destination-shaping` | 已实现 | 独立生成 Destination Contract | 观察是否在 Quick 任务中过度增加成本 |
| `repository-recon`（含 `impact-mapping`） | 已实现 | 统一产出事实、调用方、契约、生成物和回归面 | 观察结构性改动是否仍漏下游 |
| `node-delivery` + `mapflow`（含 `evidence-auditor`） | 已实现 | 节点证据与到达四问分层，防止测试绿灯被夸大 | 观察证据记录是否足够可审计 |
| `node-slicing`（对应 `map-to-delivery`） | 已实现 | 地图节点转换为声明写集和验收的 Work Item | 观察切片是否稳定而不过度模板化 |
| `product-validation` | 按需停放 | 产品价值不由工程测试推出；任务命中用户行为或业务指标时加载 `simulate-demanding-users` 或专门验证 | 真实用户/业务证据成为稳定重复需求时再独立拆分 |
| `release-action` | 停放 | 发布、部署、外部写入和凭证动作暂不进入默认链路 | 出现稳定授权、回执和回滚契约时再设计 |

演进决策规则：先在真实任务中观察触发频率、误触发成本、输入输出是否稳定，再决定新增、合并、拆分或继续由入口 skill 编排。不要为未来 provider、适配器、钩子或兼容层预先设计扩展点。

## 7. 蓝图的动态表达形式

推荐采用分层混合模型，而不是押注单一语法：

```text
blueprint.yaml                 人类编辑的语义真源
        |
        +--> JSON Schema         结构校验、版本和扩展约束
        +--> Markdown            决策解释、证据、风险和非目标
        +--> Mermaid              快速草图、评审 diff、临时讨论
        +--> Archify workflow     正式阅读、搜索、主题和导出投影
        +--> .mapflow/state.json 当前阶段、活动节点和验证投影
```

### 选择理由

- **YAML** 适合人快速改节点、边、Skill、探针和扩展字段，版本控制中的 diff 也比坐标化 SVG 清楚。
- **JSON Schema** 把稳定 ID、必填字段、枚举和 `x-*` 扩展边界机器化，防止蓝图越改越松散。
- **Markdown** 负责语义解释和证据，保存“为什么这样走”以及哪些内容只是提案；它是决策真源的补充，不重复环境中可直接查到的命令。
- **Mermaid** 适合快速画草图和讨论，不适合承载复杂布局或执行规则。
- **Archify HTML** 是可交互的正式投影，适合审查和阅读；它不反向决定阶段、门槛或状态。
- **`.mapflow/state.json`** 是运行时投影，必须与蓝图定义分离；删除或重建它不应丢失长期地图。

### 可扩展约定

语义真源建议至少包含：

```yaml
schema_version: 1
destination: {}
current_state: {}
assumptions: []
unknowns: []
boundaries: []
nodes: []
transitions: []
skill_interventions: []
evidence: []
arrival: {}
extensions:
  x-owner: personal
```

规则：

1. 节点和边使用稳定 ID，显示文字可以改，引用关系不应靠文字匹配。
2. 定义文件描述“应该怎样走”，状态文件描述“现在走到哪里”。
3. 新字段先放在 `x-*` 或 `extensions`，经真实任务验证后再提升为正式 schema 字段。
4. 展示投影可以丢弃细节，但不能改变节点语义、顺序、分支方向或验收含义。
5. 任何投影都要能回指语义 ID，便于从图、Markdown 或状态恢复到同一节点。

## 8. 三种任务分辨率

| 分辨率 | 适用 | 最小产物 | 典型耗时控制 |
| --- | --- | --- | --- |
| 小蓝图 | 局部、目标明确、立即可测 | 对话中的目的地/路径/验收 | 一次收敛，一次施工，一次验证 |
| 任务蓝图 | 行为变化、跨文件、需要复用 | 地图 + 当前工作项 | 一次只施工一个节点 |
| 路线地图 | 架构、数据、安全、迁移、外部动作、跨会话 | 持久地图 + 决策 + 检查点 | 每张路线票只解决一个关键决策 |

分辨率可以向上升级，不能为了赶速度向下降级来规避新风险。蓝图的成本应与返工风险比较：小任务使用小蓝图，大任务才支付持久化和审查成本。

## 9. 运行命令与状态投影

```bash
node .mapflow/mapflow.mjs init --destination "一句话描述目的地" --nodes N1,N2 --acceptance A1,A2
node .mapflow/mapflow.mjs status
node .mapflow/mapflow.mjs approve --node N1
node .mapflow/mapflow.mjs gate
node .mapflow/mapflow.mjs verify --node N1 --evidence "定向测试通过" --command "npm test" --observed "实际输出摘要" --model "gpt-5.6-sol" --reasoning "medium"
node .mapflow/mapflow.mjs select --node N2
node .mapflow/mapflow.mjs gate
node .mapflow/mapflow.mjs verify --node N2 --evidence "第二节点验收通过" --command "npm run scenario" --observed "实际输出摘要" --model "gpt-5.6-sol" --reasoning "medium"
node .mapflow/mapflow.mjs arrive --confirm "最终验收和 diff 检查通过" --acceptance A1,A2
```

发现新事实时，暂停当前节点并另行执行 `node .mapflow/mapflow.mjs replan --reason "新事实改变路线" --nodes N1,N2 --acceptance A1,A2`。

命令只维护轻量状态和写入门槛，不是沙箱、测试框架、产品验收器或发布系统。真实验证仍由目标仓库的命令和证据提供。

## 10. 交付回报格式

```text
完成：目的地是否达到
改动：关键文件和行为变化
验证：实际执行的命令及结果
决策：本轮需要 Owner 知道的取舍；无则写“无”
遗留：未完成、未验证或风险；无则写“无”
```

这份回报和地图、状态文件共同构成可续接记录。只有在完成节点验证和到达审计后，才把工程状态写成 `arrived`。
