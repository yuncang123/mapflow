# 图书管理系统演化演示

这不是一张预先生成好的最终地图。`npm run demo:evolution` 会创建一个临时 Git 工作区，并通过真实 Mapflow CLI 产生：空白、两枚迷雾、现场勘探、目的地合同、独立人工确认、分段反向回归、候选链整体审阅、正式 Blueprint、按需授权、沿边 Evidence 和到达审计。

正式路线不是线性清单。核心旅程确认后，先形成代码开工前的工程设计文档网络：领域模型与 API / 持久化契约是两条共享起点、互不消费对方输出的设计边；两份文档分别完成后，`engineering-design-ready` AND Join 才满足，设计评审边才开放。只有评审冻结 `engineering-design-reviewed` 后，目录/搜索与借还生命周期的实现分支才出现；两条实现边分别留下 Evidence 后，`independent-slices-ready` AND Join 才满足，集成边才开放：

```text
核心旅程已确认
      ├─ 领域模型设计文档 ─┐
      └─ API / 持久化契约 ─┤
                           ▼
                  工程设计文档均已形成
                           │
                    设计评审并冻结
                           │
             ┌─ 构建目录与搜索 ─┐
             └─ 构建借还生命周期 ┤
                                  ▼
                         两个独立切片均就绪
                                  │
                           集成与自动验证
                                  │
                             人工演示验收
```

两条独立工作边共享同一起点与 Join，但不是一条边的两个步骤：看板会把它们画成左右分开的分叉—汇合通道，并分别保留 Brief 与 Evidence。个人版仍一次只激活一条 Run；普通本地边直接启动，只有旅程决定与最终演示这类 Brief 明确保护的边才请求授权。这里证明的是可独立推进性，而不是伪造并发执行记录。

个人运行时仍只允许一个 `active` Edge Run，因此 fixture 为了确定性依次执行两条设计边、评审边，再依次执行两条实现分支；历史帧会明确保留每个 AND Join 曾经等待另一条独立边的状态，这与“两个 Agent 同时写代码”不是同一个承诺。

每条 Brief 同时带一个小型岗位 `handoff` 和上下文预算。演示中的 `human:demo` 和检查结果都是确定性 fixture，只证明 Mapflow 产品链路可回放，不代表真实项目已经实施或获得用户验收。

```bash
npm run demo:evolution
```

浏览器打开脚本打印的本地地址，在“地图演化镜头”中从第一帧播放。
