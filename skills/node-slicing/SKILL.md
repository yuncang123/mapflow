# node-slicing：切出施工节点

把地图上的一步变成一个执行者可以领取、实施、验证和回报的 Work Item。它只细化当前节点，不重新选择目的地，也不把整张地图变成一次性大任务。

## 输入

- 已批准的 Blueprint Map。
- 当前唯一节点 ID 及其 `from`、`to`、前置条件、写入面和验证。
- 目标仓库的本地约定；需要补事实时回到 `repository-recon`。

如果节点没有明确出口条件、写入面或验证方式，停止切片并返回 `blueprint-planning` 修图。

## 产出

形成 Work Item（本仓库可使用 `templates/work-item.md`，安装目标仓库使用 `.mapflow/templates/work-item.md`），至少包含：

```yaml
kind: work-item
schema_version: 1
map_ref: "blueprint map"
node: N1
goal: "本节点完成后用户或系统得到的结果"
writes: ["允许修改的文件、目录或生成物"]
non_goals: ["本节点明确不做的内容"]
preconditions: ["必须先成立的事实或 gate"]
verification: ["实际要运行的命令或观察"]
rollback: "失败时的回退或重规划入口"
```

## 步骤

1. **对齐节点**：复制节点的目标状态和出口条件，确认 Work Item 不改变 Destination Contract 或地图顺序。
2. **限定写集**：把允许修改的文件、目录、配置和生成物列到可检查的粒度；同时写出非目标，防止“顺手”扩大范围。
3. **补施工条件**：记录当前 gate 要求、依赖的前置节点、可用命令、测试 seam 和需要用户授权的动作。
4. **定义验证**：将节点验收拆成便宜检查、定向测试、必要的集成/界面检查和 diff 检查；只保留能证明该节点 `to` 状态的检查。
5. **选择模式**：行为变化且测试形状清楚时可在 Work Item 中标注 `tdd`；明确 bug 可标注 `diagnosing-bugs`；跨边界或非微小改动可标注 `code-review`。这些是执行模式，不是本节点的额外写集。

## 完成条件

- Work Item 唯一引用已批准地图节点，且目标状态与节点一致；
- 写入范围、非目标、前置条件、验证命令和失败/回退路径均可判断；
- 任何超出当前节点或需要新授权的动作都被列为阻塞或重规划条件；
- 执行者无需重新猜测“做什么、改哪里、怎样算完成”。

## 边界

- 不重写目的地、不修正整张地图、不直接实施代码。
- 不把未来节点的文件预先加入写集；跨节点依赖必须先在地图中表达。
- 不把测试计划当成测试结果；结果由 `node-delivery` 产生并记录。
